# WEB-C1 graph-bound platform qualification launch plan

Status: **implemented as a fixture-only compiler; no real plan exists, evidence is incomplete, and launch remains unauthorized**

## Purpose

The startup descriptor binds immutable worker bytes and one Browser session lifecycle to a private transport. A real qualification launcher also needs a platform enforcement contract covering executable identity, peer identity, parent death, process-tree cleanup, sandboxing, egress denial, resource limits, and deadlines.

The launch-plan compiler freezes those inputs without executing them. It produces an auditable plan whose state is always `BLOCKED_EVIDENCE_REQUIRED` until separate platform receipts prove every control.

## Inputs

The compiler consumes two compact canonical JSON files beneath one canonical packet root:

- `hepta.servo.worker_startup_descriptor.v1`;
- `hepta.servo.worker_launch_policy.v1`.

Both files must be non-symlink regular files with exactly one hard link and no group/world write permission. Paths are repository/packet relative and contain no absolute or platform-ambiguous components.

## Supported platform profiles

The first frozen profiles are:

| Platform | Target | Private transport | Executable binding | Peer identity | Parent death / cleanup |
|---|---|---|---|---|---|
| Linux x86_64 | `x86_64-unknown-linux-gnu` | inherited Unix socketpair | read-only FD, `fstat`, proc-FD execution | spawned PID + peer credentials | PDEATHSIG + process-group kill/reap |
| macOS arm64 | `aarch64-apple-darwin` | inherited Unix socketpair | read-only FD, `fstat`, spawn file actions | spawned PID + peer credentials | parent monitor + process-group kill/reap |
| Windows x86_64 | `x86_64-pc-windows-msvc` | SID-restricted named pipe | read-only file handle identity before CreateProcess | spawned PID + token SID + named-pipe client PID | Job Object kill-on-close + tree reap |

A policy cannot mix a target, transport, executable strategy, identity strategy, or cleanup strategy from another platform.

## Policy requirements

Every policy must:

- require sandbox enforcement;
- require default-deny egress enforcement;
- disable network listeners, filesystem control endpoints, and external network;
- bind four distinct SHA-256 policy objects:
  - sandbox;
  - egress;
  - profile-root;
  - resource policy;
- specify bounded startup, command, teardown, memory, CPU, process, open-file, and output limits;
- keep admission, operator acceptance, promotion, and all thirteen authority fields false.

The compiler rejects booleans masquerading as integers, out-of-range values, teardown deadlines longer than command deadlines, command deadlines shorter than startup deadlines, duplicate policy digests, unknown fields, duplicate JSON keys, and secret-bearing keys.

## Output

`hepta.servo.worker_qualification_launch_plan.v1` binds:

- exact Servo commit/tree;
- startup descriptor path, SHA-256, and self-binding ID;
- session ID, generation, and owner epoch;
- worker path, SHA-256, and bytes;
- receipt graph manifest and verification bindings;
- platform/target/transport and all enforcement strategies;
- policy digests and resource/deadline limits;
- a mandatory fresh graph reverification at launch;
- empty slots for ten independent enforcement receipts;
- full false runtime and authority posture;
- `admission_state=BLOCKED_EVIDENCE_REQUIRED`;
- decision `GRAPH_BOUND_PLATFORM_LAUNCH_PLAN_NOT_ADMITTED`;
- a domain-separated self-binding plan ID.

Output is compact canonical JSON, create-only, mode `0600`, fsynced, and never overwritten.

## Evidence still required

A plan contains no enforcement receipt. Before any qualification launch, an independent launcher must produce and bind:

1. executable-handle identity/TOCTOU receipt;
2. OS peer-identity receipt;
3. sandbox installation receipt;
4. egress-denial receipt;
5. private profile-root receipt;
6. resource-limit receipt;
7. listener scan receipt;
8. parent-death receipt;
9. descendant cleanup receipt;
10. deadline kill-and-reap receipt.

The strict graph must also be reverified immediately before launch. Only after all evidence is generated by the exact platform launcher may a separate qualification admission decision be considered. This plan itself never grants that admission.
